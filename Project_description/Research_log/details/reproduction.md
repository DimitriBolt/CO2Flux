## Notebook

Откройте весь проект CO2Flux, затем `Project_description/Research_log/01_october_2017.ipynb`.
Рабочая папка ядра должна находиться внутри проекта. Выполните все ячейки сверху вниз
в новом ядре. Для чтения на GitHub запуск не нужен: рисунки сохранены в notebook.

Первая ячейка вызывает `load_october()`: проверяет контрольные суммы семи CSV,
пересчитывает результаты из измерений и сравнивает шесть таблиц с эталонами.
Остальные четыре ячейки вызывают построение рисунков. К Oracle глава не подключается.
Технические предупреждения загрузки доступны в переменной `load_warnings`;
они не загромождают основной текст. При проверке 27.09.2026 были предупреждения
об изменении файлов реализации относительно первого паспорта, при этом все
шесть численных эталонов совпали. Ошибки проверки не подавляются.

### После изменения Python-модуля в открытом notebook

Ядро Jupyter сохраняет импортированные модули и созданные объекты в памяти.
Поэтому после обновления `chapter02.py` старый `report` может не знать новый
вид рисунка. Например, ошибка с перечнем `raw, counts, stuck, coverage` при
`report.show("example_trend")` означает использование прежней версии класса.
Номера строк в таком traceback могут не соответствовать обновлённому файлу на диске.

В [главе 2](../02_monthly_changes.ipynb) первая ячейка перечитывает `chapter02`
через `importlib.reload()` и открывает готовую таблицу окончательных результатов.
При изменении общих модулей надёжный способ — перезапустить ядро и выполнить
все ячейки. Текущий полный расчёт и явное обновление снимка описаны
[в методике главы 2](02_data_checks.md#archive-trajectories).

## Тот же расчёт в PyCharm / обычном Python

Откройте и запустите [chapter01.py](../chapter01.py): получите те же четыре рисунка.
Для использования в своём коде из корня проекта:

```python
from Project_description.Research_log.chapter01 import load_october

report = load_october()
print(report.result.summary)       # месячные параметры
print(report.result.lags)          # месячные сдвиги и дневные квартили
print(report.result.daily)         # все дневные модели
fig = report.figure("daily")      # raw, trend, diurnal, daily
fig.savefig("daily.png", dpi=160)
```

Дополнительные таблицы: `report.table("peak_quartiles")`, `report.table("intervals")`,
`report.table("excluded_days")`, `report.table("example_peaks")`,
`report.table("example_lags")`, `report.table("counts")`, `report.table("runtime")`.
Они возвращают `pandas.DataFrame`; их можно смотреть в PyCharm или выводить в ячейке.

`report.verify()` повторяет сравнение шести таблиц. Допуски `atol=rtol=1e-7`
учитывают округление исходных эталонных CSV. Это проверка повторяемости вычислений.

## Окружение и экспорт

### Локальные ссылки из notebook в PyCharm / KDE

В PyCharm 2026.2.1 щелчок по относительной ссылке в notebook на компьютере автора
открывает безымянное окно с исходным Markdown и неверным отображением кириллицы.
25.09.2026 проверен владелец этого окна: процесс `cef_server`, дочерний процесс
PyCharm. Это окно встроенного браузера IDE, а не Cursor или другое приложение KDE.
В журнале PyCharm при этих переходах также записано `Extension not allowed: md`.

Предыдущая попытка назначить PyCharm системным приложением для Markdown
не исправила щелчки в notebook. Ассоциации Markdown восстановлены из резервной
копии, созданный для этой попытки запускатель отключён. Прямое системное открытие
файла и переход по ссылке из notebook — разные пути обработки.

Простой обходной путь: открыть пояснение через **Navigate → File**
(`Ctrl+Shift+N` в стандартной раскладке PyCharm), например ввести `01_methods.md`
и выбрать файл из `Project_description/Research_log/details/`. Оглавление пояснений
можно открыть из дерева проекта: `Research_log/details/README.md`.
Это открытие файла вручную; сам переход по ссылке из notebook пока не исправлен.

В установленном плагине есть параметр `jupyter.editor.markdown.render.mode`
с вариантами `notebook_cef` и `swing`. Описание второго прямо предупреждает
об ограниченной поддержке Markdown. Он не включался: сохранение уже работающих
формул и иллюстраций важнее этой небольшой проблемы навигации. Ссылки GitHub
и содержимое notebook не менялись.

## Получение исходных данных

Выбран интервал **[01.10.2017 00:00, 01.11.2017 00:00)**: начало включено,
1 ноября исключено. Временная шкала - поле `LOCALDATETIME` из базы, без
преобразования часового пояса. CO₂ в базальте выбран по `variableid=9`.

| Уровень | Код датчика | sensorid |
|---|---|---:|
| D1 | LEO-W_4_-4_1_GMM222 | 994 |
| D2 | LEO-W_4_-4_2_GMM222 | 1010 |
| D3 | LEO-W_4_-4_3_GMM222 | 1026 |

SQL-запрос получения измерений после разрешения кодов в ID:

```sql
SELECT localdatetime, sensorid, datavalue
FROM leo_west.datavalues
WHERE localdatetime >= :start_datetime
  AND localdatetime < :end_datetime
  AND variableid = :variable_id
  AND sensorid IN (:sensor_d1, :sensor_d2, :sensor_d3)
ORDER BY localdatetime, sensorid
```

Параметры: начало/конец, указанные выше; `variable_id=9`; ID 994, 1010, 1026.
Коды разрешались отдельным запросом к `leo_west.sensors` с проверкой однозначности.
Здесь запрос не запускается: читается [снимок выгрузки](../data/ch01/README.md).

Расчёт использует общие функции из
[plot_column_timeseries.py](../../sensorDB/plot_column_timeseries.py) и
[diurnal_analysis.py](../../sensorDB/diurnal_analysis.py). Параметры главы явно
восстанавливаются из её паспорта данных, независимо от последующих настроек
обычной программы. Сохранённые эталонные таблицы используются только для проверки
нового расчёта, а не вместо него.
